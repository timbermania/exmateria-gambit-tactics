# ADR-0047 audit notes

Audited 2026-08-28, during the de-amendment pass (two dated addenda folded).
Graded against `tools/parse_abilities.py`, `src/gpu/shaders/stage_compute.glsl`,
`src/gpu/shaders/combat_common.glslinc`, `src/gpu/GPUBatchSimulator.gd`,
`docs/gambit-rules.md`, and the B8 gambit scenarios.

## Verdict

`complete`. All six decisions ship. Two ship in a shape the body contradicted,
and both are now the body text with the original under **Considered options**.

## Claims corrected in the fold

- **"State lives per-(unit, ability_id) on the GPU unit struct … a
  `cooldown_ready_at[512]` int array … (~2 KB/unit)."** Wrong on all three
  counts since #85. It is a dedicated SSBO at binding 9
  (`GPUBatchSimulator.gd:77`, `:583`), `MAX_COOLDOWN_ABILITIES = 128`
  (`combat_common.glslinc:517`), 512 B/unit. It was pulled *out* of the struct
  precisely because `copy_unit_to_next` walks `UNIT_SIZE` ints per unit per tick
  and per-commit state does not belong in that copy — a reason the ADR's original
  "the buffer is comfortable with it" shrug had no way to anticipate. The
  "Shader version bump" consequence, which described this as a unit-struct
  change, went with it: the bump landed, and the rule for future layout edits is
  ADR-0001's, not this ADR's.
- **"Default value: 60 ticks."** 300 since #93 (`parse_abilities.py:176`). The
  addendum recorded the raise; the Decision still said 60, and so did the
  `Ability cooldown` glossary entry in `docs/context/02-combat-buffer-layout.md`
  (corrected in the same commit). The 60-tick subsumption argument — smallest
  value universally subsumed by any non-zero CT — is *lost* at 300, and does not
  need recovering, because the commit-time start makes the floor invisible to
  CT-bearing abilities anyway. That is stated in dec. 2 rather than left implicit.
- **"One field, one shape, no exemption list."** True as authored — there is no
  *curated* list — but the shipped `cooldown_pre_validate` exempts two things
  structurally: `ATTACK`/`MOVE` (no `ability_id`) and any `ability_id >= 128`
  (summons, cinematic spells). Stated in dec. 1 now, since a reader checking the
  shader against the ADR would otherwise read the exemptions as a violation.
- **Single-buffering is load-bearing.** `stage_compute.glsl:445-450` documents
  that the SSBO is deliberately single-buffered so a commit written earlier in
  the same tick is visible to the next slot's veto — without it, two slots naming
  the same ability could both commit on one tick. Promoted into dec. 4; the ADR
  had no equivalent.

## Deleted, and why

- The `#86` trace-drift addendum's *diagnosis narrative* (the handoff path, the
  `/diagnose` run, the ±12 arithmetic, the deterministic `[0, 68, 136, 204, 272]`
  tick list). What survives is the rule a future reader needs: a gap read off the
  host frame is not the floor; recover the GPU commit tick from the SSBO. The
  measurement was of one run on one machine.
- The `#93` addendum's run report (`76 PASS / 0 FAIL / 4 XFAIL / 0-1 XPASS`,
  "~0.83 ATTACK commits per cycle"). A suite tally is a fact about a tree that
  has since moved.
- **"The B6 `monk_secret_fist_target_on_peak_no_cast_position` XPASS cleared
  incidentally."** Deleted as *no longer true*, not merely as transient. That
  scenario still carries an `xfail` today, and its `xfail_reason`
  (`scenarios_B_fallthrough.gd:424`) says the opposite in capitals: "THE MARKER
  IS CORRECT; THE REPORTED XPASS IS NOT," with two defects underneath it (#432
  `committed(ATTACK)` matching any entry into ACTING, #433 the ADR-0052 depth
  mirror moving the tiles). Nothing about the cooldown work is evidence about
  that scenario.
- **"The strict `>=1 per cycle` bar remains XFAIL, tracked in #93."** #93 is
  closed and `secret_fist_alternates_with_attack_fallback` carries
  `"xfail": []` with `min_fallback_per_cycle: 1`. The bar passes; it is now
  listed under Verification as dec. 2's regression guard.

## Left open

The 60 → 300 raise required a second, uncoupled edit: both B8 scenarios' tick
budgets (`max_ticks` 300 → 1000, and 800 on the alternation scenario) exist only
to fit `min_casts` observations at the current default. A future retune of
`DEFAULT_COOLDOWN_TICKS` silently starves those scenarios of casts and they fail
as "only N cast(s) observed," which reads as a cooldown regression rather than a
budget one. Proposed guard is in the register's `proposed_guard` column.
