# ADR-0014 — audit notes

*Verified 2026-08-28. ADR-level verdict: `complete`. Produced by the de-amendment rewrite that folded this ADR's two addenda into the body.*

Both decisions and the promoted third are built. Dec. 1: `EffectTimeline.gd` holds `_time_scale_data`, `_update_time_scale`, `_phase1_was_finished_last_frame` and the two phase-local cursors; `time_scale_factor` is absent from `ParticleSubsystem.gd`, so the reach-back is really gone. Dec. 2: `ScreenSubsystem._deliver_output` calls `ScreenEffectOverlay.update_layer_gradient` and `PaletteSubsystem._deliver_output` calls `MapTintOverlay.update_stack` / `UnitTintOverlay.update_stack`, both from inside the subsystem; `EffectInstance._process` carries a comment where the reach-in block used to be. Dec. 3: `phase1_finished()` / `phase2_started()` live on `EffectTimeline` and `ParticleSubsystem` reads through them.

## The derivation the ADR named is not the derivation that shipped

Dec. 1 said the timeline derives `for_each_local_frame` as `effect_frame − phase1_duration`. It does not: `EffectTimeline._advance_one_frame` increments `_p1_local_frame` / `_for_each_local_frame` once per frame their phase is open, and does so *before* `_update_time_scale` reads them. Numerically the cursor is one ahead of the subtraction at the moment the factor is computed, and the code comments say that stepped order is what the pre-capstone particle phase-controllers' `current_frame` supplied. So the shipped form is the faithful one and the ADR's formula was the approximation; the body now states the cursor.

## Stale symbol claims corrected in the rewrite, each grep-proven

- `.update_layer` is not what the color subsystems call. The live sinks are `update_layer_gradient` (screen) and `update_stack` (map/unit tint). The same stale word was sitting in `docs/context/15-effect-orchestration.md` and is fixed there in the same commit.
- `_build_sound_track` does not exist anywhere in the repo, so "internal sound-parser helpers (`_build_sound_track`, etc.)" named nothing. The surviving data-side "track" uses are the ROM `.BIN` filenames and the audio-path term.
- `Keyframe.track_enable` is **not** a field on `CameraData`. `CameraData.Keyframe` has `flags`. `track_enable` is the FFT engine's own name for that bitmask in the on-disc struct, documented at `research/key_documents/STRUCTURE_DEFINITIONS.md:878`.
- `get_caster_delta`, `set_tracks`, `track_name`, `tracks_by_context` and `PaletteTrackController` are all absent from the tree — the renames the addenda recorded really landed, which is why the manifest could go.

## Filed rather than fixed

That is a code defect, filed as issue #675. The rewrite states the measured position instead, and the same wrong sentence — imported into ADR-0012 by the previous iteration of this pass — is corrected in the same commit.
