## Harvested: On mechanizing this ADR

*Verbatim from the ADR body. The rewrite deletes the original; this is the copy.*

Decision 1 is mechanized (`check_rosters_retired.py`, four arms) and decisions
4, 6 and 7 have test coverage. Two arms are missing and are cheap:

- **Decision 3's boot scenario is unguarded and demonstrably fragile.** A guard
  asserting that `config/tune_overrides.json` carries no `scenario.active_id`
  would have caught the *Built* §5 defect at commit time, and would catch the
  next sync that reintroduces it. Whether that is *wanted* is a judgement — see
  the open question.
- **Decision 2 is unguarded.** An arm asserting `CharacterCatalog` publishes no
  `enemy_units` accessor is a one-line text net over the same walk, and is the
  arm that stops the symmetric-overlay shape being re-added by someone who did
  not read ADR-0078.

### Open question for a human — should the pinned scenario be guarded, or is it none of the guard's business?

1. **Guard it.** The pin silently changed which battle the arena boots, made a
   BUILT ADR's own numbers wrong for anyone who checked the branch out, and has
   toggled seven times. A guard on `scenario.active_id` in the tracked overrides
   file makes that visible at commit time.
2. **Leave it.** `config/tune_overrides.json` is deliberately a scratch pad for
   committed debug picks — the ADR itself calls the pin *"a user pick in a shared
   file, and changing it is its own decision"*. A guard would fire on the file's
   intended use and get switched off, which is the failure mode
   `check_rosters_retired.py`'s docstring already warns about for a different arm.

Not resolved here. Either way, *Built* §5's "Not fixed here" is now stale on this
checkout and should not be read as a live defect report.
